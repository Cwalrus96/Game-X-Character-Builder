# Campaigns

Status: complete locally September 30 and released October 1, 2026 (`WPG-CAMPAIGNS`). [Release verification](campaign-release-2026-10-01.md) records the user's explicit authorization, live rules and portrait configuration.

Any signed-in user can create a campaign. Its immutable creator (`ownerUid`) initially serves as GM and may assign any current member instead. Campaign GMs have read-only access to linked character sheets, not accounts, character collections, builder writes or portrait writes. The historical `gm` custom claim remains the separate **Super GM** privilege; ordinary campaign roles never create custom claims.

Players join deliberately using a 128-bit cryptographically random code or its equivalent invite link. Only direct authenticated invite lookups are allowed; there is no campaign or invite directory. My Campaigns queries `memberUids array-contains currentUid`. The creator can replace or disable the invite. A campaign supports up to 500 members, bounding the membership document; the number of campaigns is not globally queried or capped.

### Campaign deletion (October 10 corrected semantics)

The creator can delete a campaign from its detail view. The existing `confirmCampaignChange` dialog supplies a specific title/action label, an explicit “Are you sure” message and default Cancel focus; Cancel, Escape and close make no writes. The existing pending-operation/navigation guard wraps the request. Assigned GMs, members, outsiders and a Super GM who is not the creator cannot delete it.

`campaign-store.deleteCampaign` first atomically replaces the campaign with an immutable `{ ownerUid, deletedAt }` tombstone and deletes its active invite. This removes settings, name, roles and active membership regardless of roster size. It disappears from membership queries and immediately revokes future GM sheet/portrait reads. An ID cannot be reused or restored to reactivate old relationships. The creator then removes paired character links/roster records in pages of five and member records in pages of twenty, within the Firebase Rules access budget. Filtered server queries reveal only links for this deleted campaign, and refreshed retries preserve a character moved concurrently to another campaign. Character documents, revisions, trained skills, play state and portraits remain intact. Missing active membership removes campaign restrictions, and stale builder saves still require reload. There is no restore UI.

If cleanup is interrupted, sharing remains revoked and the creator can retry **Finish deletion** at the same detail URL. Already removed links are harmless on retry. Only the immutable tombstone remains after successful cleanup. Firebase grants the creator narrowly scoped read/delete access to that deleted campaign's child relationships and matching per-character links; it grants no character or portrait writes and no unrestricted link query. This replaces the October 1 dormant-link retention behavior.

### Campaign settings (October 1 local extension)

The final origin-selector browser check exposed a cached pre-settings Rules module. The origin entry point, widget and Rules import now carry updated asset versions; a fresh local load excludes the unavailable Curse option. The final unit rerun still passes all 716 tests. Review screenshot: `.staging/campaign-settings-review.png`.

Optional `campaigns/{id}.settings` stores `unavailableClassKeys`, `unavailableOriginKeys` and `settingSkills`. Missing settings on existing campaigns mean unrestricted choices and no custom skills. Class/origin entries use catalogue keys (up to 50 each). Up to **10 custom Setting Skills**, each with a name (1–96 characters) and description (up to 1,000 characters), fit the tested Firestore rule evaluation budget. Skill identity uses the shared canonical skill-name/key boundary; duplicate identities are rejected by the editor/store. A name change is a new available choice, never an automatic rename of learned ranks. Equal existing skill identities share training rather than creating a second paid row.

Settings are editable at creation and afterward by the creator or current assigned GM. Other members can inspect them. Only the creator still changes the GM, campaign name, invitations and membership. A settings save uses a transaction and rejects a changed base; the page presents a cancelable confirmation. The campaign document does not gain access to character writes.

The user explicitly chose **custom skills** and **compatible characters before joining**. Adding or switching a character checks class/origin compatibility in the same transaction as the paired links; Firebase independently checks the actual character. A failed switch preserves the previous link. Linked owners cannot select newly forbidden class/origin values through direct character updates, including a delete/recreate bypass. If the GM changes restrictions after a character is already linked, the existing class/origin remains intact with builder warnings. Existing paid skills also survive skill-list edits, leaving or changing campaigns. No bulk character rewrite or automatic point refund occurs.

Every session-based builder page and the character sheet load a per-character campaign context alongside the immutable shared catalogue. Pure campaign Rules filter acquisitions and produce graph errors for new forbidden choices; existing choices produce informational warnings. Skill Rules projects campaign skills as untrained choices, uses the normal point costs/caps and feeds ordinary skill/Technique prerequisites, dependency review and sheet rolls. Paid ranks stay in the existing `builder.sheet.repeatables.settingSkills` format and use `SetSettingSkills`, CharacterSession, graph reconciliation and the existing reader/writer. No new character schema, duplicate skill model, free rank or campaign field is persisted in a character. The Profile page retains its narrow name/portrait-only patch path.

Before a builder save, the page checks current server campaign settings/membership against its loaded context. A changed context stops saving with a reload explanation, retaining pending state. This guard supplements server compatibility checks; it is not authorization. The sheet remains a read-only consumer of skill definitions and cannot autosave derived skill rows. Super GM can get a known valid campaign to project a viewed character correctly, but still cannot enumerate all campaigns through an unconstrained query.

- `campaigns/{campaignId}`: name, immutable ownerUid, gmUid, memberUids, inviteCode (empty when disabled), createdAt, updatedAt.
- `campaigns/{campaignId}/members/{uid}`: uid, displayName, joinCode, joinedAt. Only the joining user supplies their own public display name; account email/profile documents remain private.
- `campaignInvites/{code}`: campaignId only. Code ownership is immutable; replacement invalidates earlier codes against the campaign's current value.
- `users/{uid}/characterCampaigns/{characterId}`: campaignId, rosterId. One campaign per character. Separate from canonical character documents and their revisions.
- `campaigns/{campaignId}/characters/{rosterId}`: ownerUid, characterId. An atomic transaction pairs roster entries with the character link; names and sheet data come from the actual character, not a copied character model.

Firestore rules validate shape, immutable ownership, invite proofs, membership transitions, GM assignment and reciprocal character links. A character read follows its link to the current campaign, verifies the requesting GM and the owner's active membership. Storage uses the same two-document authorization lookup. Other members may read campaign membership and roster references, but not other players' sheets. The creator can remove members; noncreator/non-GM members can leave. Reassign a departing GM first. The creator remains a member. Removed members' links remain dormant; joining again restores them while the campaign is active. The UI explicitly explains this behavior. A player can detach their own character even after leaving or campaign deletion. Ownership transfer remains unavailable.

`campaign-store.js` owns campaign and relationship persistence, not character saves. Character roster reads use the existing database reader. Campaign GM sheet routes suppress builder navigation, initialization, temporary-state autosave and appearance writes; Firebase rules independently deny writes. Owner and Super GM behavior remains compatible. Existing character documents need no migration.

Character campaign changes show a save result. Page navigation and sign-out wait for pending campaign writes through the existing navigation guard. Membership-changing actions, invite replacement/disable and character switches/detachment use an accessible confirmation dialog backed by the existing dialog lifecycle; Cancel, Escape and close are side-effect free. Confirmed snapshot handling avoids opening protected children from optimistic, uncommitted membership state.
