# Repeatable Traits and September 29 data release

Repeatable Traits now occupy separate existing grant slots and retain independent child choices. A repeated Elemental Blaster chooses a different primal element; Integrated Weapon chooses a different eligible one-handed or versatile base; Combat Training chooses a different combat discipline and one eligible Technique. Non-repeatable Traits retain their previous duplicate restrictions. This does not create extra Trait capacity.

## Shared policy and storage

`trait-option-rules.js` defines child identities, permitted values, duplicate checks and provider contexts for every acquisition source. Identity includes the acquisition instance, Trait definition, local choice and slot. Long identities use a bounded deterministic hash; source ownership is checked independently. Different sources may grant the same repeatable Trait, but its option must remain distinct for the same recipient.

Children use the existing schema-6 `builder.grantChoices` envelope with `type: "trait-option"`, the Trait instance as `sourceId`, and a stable-key `value`. No new stored shape, schema version or read-time write is introduced. Existing characters with an unanswered option retain the Trait selection and receive a completion reminder; benefits requiring that option await a valid answer. The revision-aware builder save remains the only writer of these permanent choices.

The existing graph owns each child answer and derived benefit. Wrong-owner and duplicate answers are validation errors, not confirmable losses. Replacing a Trait, changing a discipline, removing a source or losing rank reviews invalid children and dependent Techniques through ordinary reconciliation. Cancel preserves the accepted character exactly. One Technique can have several valid owners while consuming no ordinary slot for a direct grant.

Integrated Weapon derives an ordinary weapon with its provider rank/skill, Natural tag and automatic base attacks. It consumes no equipment slot and is never copied into persistent equipment. Elemental Blaster grants Elemental Blast in its provider context and, from rank 2, opens compatible Elementalism selections for its chosen element. Shared Technique Rules still enforce all other prerequisites and slot limits. Trait cards and Technique ownership labels include the chosen option.

The source adapter accepts optional `Traits.repeatable` as Y/N/blank, preserving historical snapshots without the header. Invalid values and unsupported repeatable option contracts fail staging. The source Sheet was not edited.

Refreshing the full Feat catalogue exposed repeated expensive prerequisite-context construction. Feat alternatives now share their identical hypothetical context, and Trait candidates share parent eligibility work. Widget changes yield before graph work, reject repeated input while busy and cancel queued work if destroyed. A measured full-catalogue Feat check fell from about 5 seconds to 42 ms; actual browser element changes complete promptly.

## Remaining boundary

Combat Training's shared choice mechanics are implemented, but Familiar/Mech-owned Traits still await their recipient subsystems; their benefits must not leak onto the owning character. Conditional gameplay execution remains described rather than automatically applied. This feature does not close broader `WPE-DOMAIN-MIGRATION` acceptance. The next named step, `WPF-UI-SYSTEM`, standardizes controls, accessibility and navigation after domain acceptance; it is not started by this release.
