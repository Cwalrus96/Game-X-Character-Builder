## Reproduced identity and pumping defects

1. With a stored weapon whose key is `other-blade` and custom name is `required-blade`, `evaluatePrerequisite({type: 'weapon', key: 'required-blade'}, ...)` returns `ok: true` under syntax v3. A custom label must not supply an unrelated weapon identity.
2. Given an unselected feat `{featKey: 'unselected', name: 'selected'}` before the selected feat `{featKey: 'selected', name: 'Chosen Feat'}`, a builder with `selectedFeats: ['selected']` incorrectly meets the prerequisite for key `unselected`. The first name-or-key match contaminates the selected identities.
3. A schema-3 Technique with `pumpingByRank: {1: '+1 accuracy per Energy'}` renders `+1 accuracy Damage per Energy`. The generic source text was valid; presentation changed its meaning.

These are bounded helper-level reproductions. They warrant controlled regression fixtures when repaired; no production-character exploitation or data corruption is claimed.

## Requirements already carried across

- **Consistent removal summaries:** Class, Attributes, Origin, Skills, Equipment, Techniques and Bonds/Keystones all use `confirmCharacterChange`, including changes initiated by their nested widgets. Blocking errors remain distinct from confirmable removals.
- **Trait presentation and source ownership:** the concurrent, now-committed Trait follow-up covers Class features, selected options/feats and Origin features. Both compact and expanded views omit ineligible Traits. Read-only acquired Trait cards on the character sheet are intentionally retained.
- **Unavailable options:** Class feature/feat options start hidden; Equipment's out-of-rank toggle starts unchecked. Already-acquired entries are not erased from display merely because new acquisition would be unavailable.
- **Satisfied prerequisites:** current feat/feature option cards omit satisfied requirements; they retain unmet reasons when unavailable options are deliberately shown. Reference material without character context can still show requirements.
- **Incomplete authoring and notes:** the latest source uses declared required cells rather than notes/prose readiness guesses, and incomplete records are preserved. This is not permission to invent missing mechanics, reintroduce manual status columns, or implement held Familiar/Mech systems.
- **Basic-attack wrappers:** the new explicitly authored Unarmed Strike wrappers use stable `basicAttack` references, `rollRequired=N`, and blank independent-roll fields. The source scan found no additional mismatch among descriptions explicitly saying to make a basic attack or Unarmed Strike. Hurricane Kick's unspecified attack remains a content question, not an invented damage rule.
- **Tests:** the unit runner excludes installed-catalogue tests; published-data checks are under `tests/release` and the separate `test:data` command. Tests using named synthetic fixture records are not a dependency on editable spreadsheet content.
- **Distinct class skill roles:** `combatTechniqueSkill`, `combatSkills` and `utilitySkillOptions` remain separate; the broader consistency instruction does not mean merging semantically different fields.
- **Production and manual acceptance:** personal acceptance remains nonblocking for engineering, while the user's explicit production-deployment boundary applies across all pages and data releases.
